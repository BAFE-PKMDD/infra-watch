# INFRA Watch UI and anti-slop audit 002

Date: 2026-09-27. Scope: `infra-watch` only, current working tree. Review mode: audit existing UI. No UI changes applied.

Canonical direction: [INFRA Watch Interface Standard](../docs/06-ui-ux-design.md), plus the anti-slop core, human/accessibility, mobile-layout, and UI skills. This is a source-based audit: the configured browser session had no available browser. No screenshot comparison, click-through, or full WCAG conformance pass is claimed.

The product already has useful domain-specific structure: projects and regions, budget and progress measures, source freshness, coverage/unknown states, map evidence, and visible AI verification guidance. The strongest generic design signals are concentrated in the public landing page and photo markers. Appearance alone cannot establish whether code was AI-generated.

## Numbered findings

### 1. HIGH: citizen feedback is inaccessible by keyboard

Rules: **R-32, R-26**, interface standard sections 5 and 9. Confidence: High.

`components/public/citizen-feedback-bubbles.tsx:167` renders a draggable `motion.div` with an `onClick`, without a native button/link, keyboard handler, or focusability. The expanded card at line 49 has no dialog semantics, focus transfer/trap, Escape handler, or focus restoration. Its close button is only about 28px (16px icon plus 12px padding). The reduced-motion branch at line 283 also removes the ability to expand the truncated comment.

Recommended correction: use a semantic trigger and the existing `components/ui/dialog.tsx` primitive. Preserve the same actions and content when motion is reduced. Give close and other icon controls approximately 44px targets.

### 2. HIGH: floating feedback cards clip and overlap on phones

Rule: **R-03**, interface standard section 5. Confidence: High from layout constraints; browser confirmation still needed.

`components/public/citizen-feedback-bubbles.tsx:12` positions cards at 3%, 28%, 53%, and 54%; line 200 fixes their width at 288px below `sm`. Line 318 clips everything to a 430px-high `overflow-hidden` canvas. The parent section has 16px horizontal padding.

At a 390px viewport the canvas is approximately 358px wide. A card at 54% starts around 193px and ends around 481px, clipping roughly 123px of its width. The first pair also overlaps. Dragging is required to uncover content, and cannot substitute for a readable mobile layout. The expanded panel is constrained inside the same clipped canvas, so long comments or text zoom can also make it unusable.

Recommended correction: use normal document flow on phones, with a full-width feedback list. If retaining a special desktop composition, keep every card readable without dragging and render the dialog in a viewport portal.

### 3. HIGH: project table headers look sortable but do nothing

Rule: **R-26 / C-2**, interface standard section 5. Confidence: High.

`app/(public)/projects/projects-directory-client.tsx:941` through line 954 renders five buttons with chevrons for name/code, location, agency, budget, and status. None has a click handler. A separate sort select exists, but that does not make these buttons functional.

Recommended correction: wire supported columns to the existing sort state and expose `aria-sort` on the active header; render unsupported columns as plain header text. The table scroll wrapper at line 937 also needs an accessible label and keyboard-focusable overflow region under the project's standard.

### 4. HIGH: low-contrast, undersized metadata remains in public views

Rules: **R-25, R-34**, interface standard sections 3 and 9. Confidence: High for token contrast and source sizes.

Examples: `components/public/citizen-feedback-bubbles.tsx:238` uses 10px Slate 400 timestamps and Slate 500 in dark mode; line 295 repeats 10px Slate 400 in the static layout. `app/(public)/projects/projects-directory-client.tsx:748` uses 11px Slate 400 / dark Slate 500 explanatory text. Project IDs and status chips elsewhere in that component use 10px text.

Calculated from the installed Tailwind OKLCH tokens, normal-text contrast is approximately **2.63:1** for Slate 400 on white, **2.51:1** on Slate 50, **3.74:1** for Slate 500 on Slate 900, and **4.23:1** on Slate 950. These are below 4.5:1. These are token-pair calculations, not measured screenshots of every composited surface.

Recommended correction: use at least 12px metadata, normally 14px for controls and important labels, and choose foreground tokens that pass on each actual surface. Test both themes and 200% text zoom.

### 5. MEDIUM: ornament and motion compete with infrastructure information

Rules: **R-01, R-07, R-10, R-12, R-19 / C-1**, interface standard sections 1 and 8. Confidence: High for style usage; visual judgment remains source-based.

Concrete examples:

- `app/(public)/landing-page-client.tsx:238` and `:269`: glass surfaces, large shadows, rotating/scaling official-seal containers. Lines 465–484 add gradient stripes, shimmer, and rotating icons to program cards.
- `components/public/citizen-feedback-bubbles.tsx:180`: perpetual floating, drag behavior, glass cards, hover enlargement, and a dotted background. These add effort to reading actual public reports.
- `components/projects/photo-marker.tsx:18`: repeated glass, gradients, pulse/glow rings, and large shadows around map photos, contrary to the canonical indigo/slate system.
- `components/voice/ania-voice-orb.tsx:41`: glossy multicolor gradient symbolism where the standard calls for restrained assistant presentation. It does respect reduced motion; do not remove that existing safeguard.

Recommended correction: keep the real project photography and geographic context as the identity. Use a flat official masthead, clear project-search/report actions, factual project measures, a readable citizen feed, and solid selected-marker states. Keep motion for real state changes. The dark photographic hero overlay can serve readability; it should not be removed just because it uses a gradient.

### 6. MEDIUM: the landing hero does not honor reduced motion

Rule: **R-19**, interface standard section 9. Confidence: High from source inspection.

`app/(public)/landing-page-client.tsx` contains entrance translations, scaling, rotations, springs, and hover transforms, but neither reads reduced-motion preferences nor inherits an observed global `MotionConfig` policy. The landing feedback section also animates its wrappers independently of its reduced-motion child. Other components already implement `useReducedMotion`, so behavior is inconsistent.

Recommended correction: apply a shared reduced-motion policy and disable nonessential transforms for that preference while preserving all content and controls. Do not claim that a static child alone disables its parent animations.

### 7. LOW: assistant naming is inconsistent across the same interaction

Rules: **R-20 / C-1 (deliberate identity)** and the canonical naming in interface standard sections 8 and 10. Confidence: High.

`components/ai-assistant-widget.tsx:382` announces “Open ARIA”; line 427 titles the panel ANIA or InfraWatch AI; line 451 uses those different names for closing it. The server prompt also identifies ARIA. The existing identity test fails.

Recommended correction: agree on the public and administrative names, then use those consistently in visible headings, accessible labels, voice copy, prompts, and tests. This is an identity consistency issue, not evidence that the AI is unsafe.

## Audit gate and limits

This is a findings report, not approval to release a redesigned UI. Applicable gates were evaluated against source:

- R-03: **FAIL**, fixed-width feedback cards are clipped by the mobile canvas (finding 2).
- R-25 and R-34 contrast: **FAIL**, the named token pairs miss normal-text AA contrast (finding 4).
- R-26 / C-2: **FAIL**, table-header buttons have no action (finding 3).
- R-32: **FAIL**, feedback triggers and popup lack keyboard behavior (finding 1).
- R-01/R-07/R-10/R-12/R-19 purpose: **FAIL**, repeated ornament conflicts with the explicit product standard (finding 5).
- R-37 direction: **PASS**, the existing canonical interface standard provides the direction.
- R-23/R-33 for this review: **PASS**, no visual assets were generated and no application UI was rewritten.
- R-35 runtime and remaining theme/breakpoint gates: **UNVERIFIED**, no browser was available. No click-through is claimed.
- Evidence checks R-17/R-18/R-36/R-38: the reviewed feedback component receives actual feedback records; no fabricated testimonials were identified there. The complete site's statistics and claims were not independently reconciled to a live database.
- Remaining navigation, all form states, and page-wide composition: not exhaustively verified. No blanket pass is assigned.

The skills' build-delivery gate requires fixes before shipping a UI, while this task requests a review. The failures above are therefore retained as actionable findings. Application changes require a separate implementation task. Prioritize findings 1–4, then address motion and visual simplification in findings 5–6.
